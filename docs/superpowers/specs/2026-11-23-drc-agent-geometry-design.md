# DRC Agent Geometry and Replanning Design

## Goal and scope

Create the violation checklist deterministically from the parsed DRC report, and use a model-generated plan to guide internal FAGENT tools that identify, measure, propose, apply and recheck geometry repairs. Start with the CT–M1 enclosure/coverage case as a representative supported subset; design tool contracts to accommodate other rule families. The agent discovers rule information from the configured DRC deck and RAG rather than relying on per-project rule configuration. All geometry operations execute inside FAGENT with existing Python capabilities; do not invoke external applications as part of these tools.

An operator may later run a real DRC engine on the candidate; a local geometry check is not an equivalent or a DRC-clean declaration. Unsupported or ambiguous cases remain unresolved with evidence. Do not fabricate rule semantics, a polygon identity, connectivity, a repair or a pass.

## Workflow and state

1. `read` parses inputs, indexes or loads rule references, retains the original DRC report and GDS metadata, and creates one stable checklist item per reported violation using rule name, source violation ID and occurrence. Record pending items without invented work or evidence; a skip requires the configured goal to explicitly exclude that category. `read` stores the full data and checklist in graph state and persists their artifacts. `drc_context` is retained as data for repair tools, not sent wholesale to the model at every request.
2. `plan` receives the relevant active violations from the DRC log, rule references retrieved from RAG, the goal and constraints, and the current checklist. It does not receive `drc_context`. It returns a plan describing the ordered tool calls and their purpose; the graph stores it in `state["plan"]`. A missing, invalid, or empty plan for active work yields an incomplete result with the checklist retained, rather than proceeding as if a repair was planned. A run with no active work must be handled independently.
3. `repair` receives the plan and compact checklist, and requests per-task details via tools. `repair--tools` executes the requested Python functions and returns structured evidence. Tool calls/results remain in the conversation and trace, and state holds the current candidate, digest, checklist, plan and progress.
4. On a tool execution failure, return to `plan` with relevant violation records, relevant RAG references, goal/constraints, the failed node's request/tool/result conversation, current plan and current checklist/candidate identity. The model decides whether to preserve or change other pending actions. Preserve completed edits and prior evidence; never reset to the original geometry while claiming the candidate is current. The existing configurable iteration bound must also bound replanning so repeated errors produce a clear incomplete outcome.

The model is instructed to follow the plan through the `plan` key in its message. There is deliberately no code that enforces the tool order: deviations remain possible and must be recorded, not described as impossible. Existing editing preconditions and validation guards remain in force.

## Internal tool contracts

All calls identify the checklist task and relevant candidate revision; responses carry task/rule identity, source/provenance, units, status and evidence. Stable polygon IDs are scoped to cell and candidate revision. Use database-unit integer coordinates for geometric calculations and provide explicit conversion metadata for display. Never silently guess units or round a required dimension downward.

- `get_violation(task_id)` returns the selected report violation, marker type and coordinates, owning cell if known, rule and source, plus current task/candidate state. It reads existing state and does not duplicate a full report in each model request.
- `find_rule(task_id)` retrieves the original named rule text, related source references and layer mapping information. It reports candidates and exact source locations. Agent interpretation can guide exploration, but an interpretation alone is not proof of a rule's semantics.
- `find_related_polygons(task_id)` searches the marker area and a rule-derived or explicitly supplied search region on relevant physical layers. Return IDs, physical layer/datatype, cell, geometry, spatial relation and evidence. Distinguish a proven match from candidate geometries. Unknown source-layer mapping, derived layers, multiple matches, missing geometry, hierarchical references or paths that cannot safely be resolved must yield `ambiguous` or `unsupported` with candidates and reason. Do not confuse an error marker with an editable polygon.
- `measure_violation(task_id, polygon_ids)` evaluates only explicitly supported and verified geometry semantics; return measurement, condition, threshold, units, contributing edges, geometry revision and `pass`, `fail`, or `unknown`. It must handle missing or ambiguous input and distinguish union coverage from a single-polygon comparison.
- `propose_polygon_fix(task_id, polygon_ids)` returns zero or more candidate edits with stable repair IDs, source revision/digest, selected polygon and edge, before/after geometry, DBU delta, rule assumptions, nearby constraints, and pre/post local measurement. Proposals must be grid-aligned and deterministic for the same inputs. Any unknown semantics, connectivity, shared-cell impact, competing constraints or inability to verify the proposed change makes the affected proposal unsupported; do not label a proposal globally safe solely from local geometry.
- `apply_polygon_fix(repair_id)` checks revision and target identity, applies the selected proposal using existing edit protections, saves `candidate.gds` and its digest and polygon ID mapping, and invalidates affected evidence. Reject stale or ambiguous proposals. Preserve original input GDS.
- `recheck_violation(task_id)` evaluates the supported local geometry on the saved candidate, binds evidence to its digest and updates the task only in accordance with actual results. Local success is a limited geometric assessment, not a deck-level DRC pass. `unknown` or `fail` cannot be recorded as verified.

## Rule semantics and representative example

The existing deck's `CT_R_11` requires CT covered by M1 and by `(GT OR AA)`, with `INST` and `EXCLU` exclusions. Therefore, checking CT against M1 alone cannot establish the entire rule. `CT_EN_7a_7b` includes directional/opposite and exclusion conditions; do not reduce it to an unconditional scalar minimum. Begin with only those subcases for which the deck expression, physical layer mappings, marker/shape correspondence, relevant region and conditions are fully understood and supported. All others return `unsupported` or `ambiguous` rather than a guessed fix.

Illustrative input: a report marker identifies a contact violation, the deck and mappings identify contact and metal layers, and exactly one editable contact and metal candidate are proven relevant. If a supported enclosure condition requires 25 DBU and the measured gap is 18 DBU, a candidate could require 7 DBU of additional margin; calculate actual edited vertices from the selected edge and grid, and remeasure the full supported rule after application. These numbers are examples, not defaults. Nearby geometry, connectivity, hierarchy and rule exceptions can make the candidate invalid or unprovable.

## Data integrity and failure handling

Retain original report and GDS, record source files, layer-map and deck identity, candidate digest, DBU scale, cell/hierarchy and tool evidence. All edits apply only to an identified candidate revision. Detect stale plans and proposals after any edit; preserve a recoverable previous state if application or writing fails. Replanning must have the actual failed tool result and conversation, not an imagined explanation. No model-generated status can substitute for actual geometry or DRC evidence.

## Verification

Use representative synthetic geometry and the repository's actual CT/M1 report and deck to test parsing, unit/grid handling, marker-to-shape mapping, multiple candidates, hierarchical or derived layers, exclusion conditions, coverage unions, stale candidates, local rechecks, and preservation of unmodified geometry. Test empty model plans and tool errors/replanning, including original relevant inputs and failure conversation, with a stubbed model boundary. Compare supported subcases against independent expected geometry and, where available, real DRC output. Run the relevant regression suite and inspect generated candidate GDS and trace artifacts. State explicitly if a real DRC engine, connectivity check or full deck validation was unavailable.
